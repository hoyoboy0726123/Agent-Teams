# 寵物美容店線上預約 MVP — 測試計畫（草案 v0.1）

> 依據：@backend ER 圖 / REST API 設計（整體容量制）、@security 初步風險意見、@devops CI/CD 規劃
> 狀態：草案，待 #2 API 初版（10/10）與 #3/#4 頁面出來後補齊細節與自動化腳本

## 1. 測試範圍

| 範圍內 | 範圍外（MVP 不測） |
|---|---|
| 客人端：選服務→選時段→填寵物資料→送出預約 | 指定美容師功能（未來版本） |
| 客人查詢/取消（手機號+預約ID） | 多店家/多分店 |
| 店家端：當日排程檢視、狀態更新 | 簡訊 OTP（若未實作） |
| 容量制時段衝突/滿位邏輯 | 金流/付款 |
| Admin 登入授權 | |

## 2. 測試策略

| 層級 | 方式 | 負責 |
|---|---|---|
| 單元測試 | 衝突檢查邏輯、狀態機轉換 | @backend 撰寫，QA review |
| API 整合測試 | Postman/Newman 或 pytest，涵蓋本文件 case | @qa |
| E2E | 客人預約全流程、店家排程操作（待 #3/#4 出來後用 Playwright/Cypress） | @qa + @frontend 協助 |
| 併發測試 | 模擬同時段搶最後一個名額 | @qa（重點項，見 4.1） |
| 安全測試 | 對照 @security 的威脅表逐項驗證 | @qa 執行、@security 覆核 |
| 探索性測試 | 手動走查、可用性 | @qa |

## 3. 核心功能測試案例（節錄）

### 3.1 建立預約 `POST /api/appointments`

| # | 案例 | 預期結果 |
|---|---|---|
| TC-01 | 正常填寫服務/時段/寵物資料送出 | 201，回傳 appointment id，status=pending |
| TC-02 | 選擇已達容量上限的時段 | 409 Conflict，不寫入資料 |
| TC-03 | 缺必填欄位（如電話、寵物名稱） | 400，明確錯誤訊息（欄位層級） |
| TC-04 | 電話格式錯誤（非台灣手機格式） | 400 驗證失敗 |
| TC-05 | service_id 不存在或 active=false | 400/404，不可預約已下架服務 |
| TC-06 | appt_date 為過去日期 | 400，禁止預約過去時段 |
| TC-07 | appt_date 超出可預約範圍（如 90 天後） | 400 或依營業規則限制 |
| TC-08 | pet.notes 塞入超長文字/HTML/script 標籤 | 儲存時做長度限制；店家端顯示時需 escape，不可執行 script（呼應 @security XSS 提醒） |
| TC-09 | 同一時段边界（服務結束時間 = 下一筆開始時間） | 應視為不重疊，可預約（驗證 SQL 的 `<=`/`>=` 邊界條件） |
| TC-10 | duration_min 造成跨營業時間結束（如 17:50 開始、服務 60 分鐘，但打烊 18:00） | 應拒絕此時段（不產生超出營業時間的預約） |

### 3.2 併發/衝突（重點）

| # | 案例 | 預期結果 |
|---|---|---|
| TC-11 | 兩個客戶同時對同一時段發送最後一個名額的預約請求（race condition） | 僅一筆成功建立，另一筆收到 409，**不可兩筆都成功導致超賣** |
| TC-12 | 高併發灌單同一時段（10+ 併發請求） | 容量限制被正確遵守，DB 無死鎖/無重複計數錯誤 |

> 這是 MVP 最高風險項目：需與 @backend 確認是用 `SELECT ... FOR UPDATE` 還是 DB unique constraint + retry，QA 會寫腳本模擬併發直接打 API 驗證，而不只是靠 code review。

### 3.3 查詢/取消 `GET/DELETE /api/appointments/:id`

| # | 案例 | 預期結果 |
|---|---|---|
| TC-13 | 正確 ID + 正確手機號查詢 | 200，回傳預約資料 |
| TC-14 | 正確 ID + 錯誤手機號 | 統一錯誤訊息（不可洩漏「ID 存在但手機不符」，呼應 @security） |
| TC-15 | 錯誤/不存在 ID + 任意手機號 | 統一錯誤訊息，與 TC-14 訊息一致（防列舉） |
| TC-16 | 短時間內對同一 ID 多次嘗試不同手機號（暴力猜測） | 觸發 rate limit / 鎖定機制 |
| TC-17 | 取消已完成（completed）的預約 | 應拒絕，回傳明確錯誤（不可逆） |
| TC-18 | 重複取消同一筆已取消的預約 | 冪等或明確錯誤，不可產生異常狀態 |

### 3.4 店家端 Admin

| # | 案例 | 預期結果 |
|---|---|---|
| TC-19 | 未登入呼叫 `/api/admin/appointments` | 401 |
| TC-20 | Session/Token 過期後操作 | 401，前端導回登入 |
| TC-21 | PATCH 狀態非法跳轉（如 pending→completed 跳過 confirmed） | 依狀態機規則拒絕（需與 @backend 確認允許的轉換路徑） |
| TC-22 | 當日排程列表跨時區/日期邊界（23:59 vs 00:00） | 日期篩選正確，不遺漏/不重複顯示 |
| TC-23 | notes 欄位含特殊字元在排程頁顯示 | 正確 escape，不破版、無 XSS |

### 3.5 資料驗證/邊界

| # | 案例 | 預期結果 |
|---|---|---|
| TC-24 | pet.species 傳入非 enum 值 | 400 |
| TC-25 | 極端寵物體型/size 值 | 依 enum 驗證 |
| TC-26 | 電話號碼含特殊字元試 SQL injection payload | 無異常，parameterized query 生效（呼應 @security） |
| TC-27 | 服務列表含 duration_min=0 或負數（資料異常防護） | 後台應防呆，前端顯示異常時不崩潰 |

## 4. 非功能測試

| 類別 | 重點 |
|---|---|
| 效能 | `GET /availability` 回應時間、當日排程頁載入速度 |
| 可用性 | 手機瀏覽器（客人主要裝置）表單填寫順暢度、錯誤提示清楚 |
| 相容性 | iOS Safari / Android Chrome 為主要測試裝置 |
| 監控驗證 | `/health` endpoint 正確回報 DB 連線狀態（配合 @devops #5） |

## 5. Go / No-Go 上線標準（草案，供 #8 上線前參考）

- [ ] P0 案例（TC-01, 02, 11, 12, 13-16, 19, 26）100% 通過
