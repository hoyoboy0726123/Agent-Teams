### 🖥️ 前端工程師 Frontend Developer (@frontend) · ⏱ 134s

技術可行性沒問題——單頁 vanilla HTML/CSS/JS 即可達成 spec 全部需求，不需框架，載入快、好維護。以下是可運作的原型（含 localStorage 暫存、貪婪結算演算法、整數分帳無四捨五入誤差、手機優先版面與列印樣式）。

📎 **產出物：分帳計算器 Prototype**（website，見 artifacts/）

技術評估重點：
- 純 vanilla HTML/CSS/JS，單一檔案即可上線，無需建置流程，符合「單次使用、免登入」定位。
- **分攤誤差處理**：改用整數除法 + 餘數逐一分配（前 N 位分攤人多分 1 元），從源頭避免四捨五入誤差，確保每筆支出「已分攤總額 = 支出金額」，加總後淨額必然平衡，不需事後補差額。
- **最少轉帳次數**：採 spec 指定的貪婪演算法（最大應收 vs 最大應付互抵），符合「逼近最少交易數」的說明用詞。
- Edge cases 已覆蓋：成員 <2 人提示、無支出提示、刪除被引用成員（付款人擋刪除／分攤人確認並自動移除）、金額驗證擋 0/負數/非整數、淨額為 0 不出現在轉帳建議、全部結清顯示「不需轉帳」訊息、localStorage 自動暫存重整不遺失。
- 手機優先：單欄版面、輸入框/按鈕 ≥44px、`inputmode="numeric"`、底部 sticky「新增支出」快捷按鈕。
- 列印：`@media print` 隱藏表單與操作按鈕，卡片與轉帳項目 `page-break-inside:avoid`，A4 邊界設定。

@qa 可以直接用這個原型跑測項，特別是分攤餘數分配與貪婪結算的邊界案例（例如金額無法整除人數、單人代墊全部、已結清情境）。

### 🧪 測試工程師 QA Engineer (@qa) · ⏱ 59s

## QA Review — 分帳計算器 Prototype vs Spec

大部分 spec 需求（成員/支出 CRUD、驗證、手機版面、列印樣式、localStorage）在原型碼中都有對應實作，做得不錯。找到 **1 個必修 bug** 和幾個待確認/微調項目：

### 🐛 Must-fix
**刪除成員可能讓支出變成「0 位分攤人」**
`deleteMember()` 只擋「此人是付款人」的情況，但若某筆支出的分攤人**只剩這一位**（其他分攤人已取消勾選），刪除後 `participantIds` 會變空陣列。這筆支出金額仍存在，但沒人分攤 → 違反「已分攤總額＝支出金額」的不變量，結算金額會對不上。
- 建議：比照付款人邏輯，若刪除會導致任何支出 `participantIds.length === 0`，需擋刪除或提示使用者先修改該筆支出。

### ⚠️ 待確認（程式碼被截斷，看不到）
無法看到「淨額計算 + 貪婪結算演算法 + 餘數分配」的實際程式碼，麻煩 @frontend 確認以下行為並回覆：
1. 餘數（如 100÷3）分配順序是否固定且可重現（例如照 participantIds 順序前 N 位各多 1 元）？
2. 貪婪演算法在 3 人以上鏈狀債務（A欠B、B欠C）時是否正確互抵、不多產生交易？
3. 淨額為 0 的人是否在進入貪婪演算法前就被過濾，避免產生 0 元轉帳項？

### 🔎 次要/UX
- 金額輸入 `12.5` 會被 `parseInt` 靜默截斷成 `12`，不會顯示「請輸入整數」錯誤 — 與「整數金額驗證」精神不符，建議改用 `Number()` + 檢查小數點後拒絕。
- 編輯成員姓名用原生 `prompt()`，手機上體驗與其餘卡片式 UI 不一致，可考慮改成內嵌輸入框（non-blocking，可列入 nice-to-have）。

### ✅ 手動需驗證的關鍵測項（建議 @frontend 或 @hoyo 在瀏覽器實測）
- 100 元 ÷ 3 人、10 元 ÷ 4 人等不可整除情境，加總是否精準等於支出金額
- 多筆支出後全部結清（淨額皆為0）→ 顯示「不需轉帳」
- 單人代墊全部費用情境的結算結果
- 重新整理頁面資料是否保留（localStorage）
- 列印預覽：支出卡片多時是否真的不被分頁切斷
