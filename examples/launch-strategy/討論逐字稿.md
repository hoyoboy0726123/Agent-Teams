### 🧐 審稿人 Critic (@critic) · 17:15

## 風險排序(按嚴重度)

**1. 核心賣點可能踩到 Claude/ChatGPT 訂閱的服務條款 —— 這是致命風險,必須第一個排除**
研究裡「把訂閱制用量『借用』給多 Agent 協作」的成本故事非常吸引人,但沒人確認過:Claude Pro/Max、ChatGPT Plus/Pro 的消費級訂閱條款,通常明文限制自動化/程式化調用、轉售、或非官方 API 存取(consumer 帳號的驗證機制跟 API key 本質不同)。如果我們的實作方式是「模擬瀏覽器 session / reverse-engineer 訂閱端點」去驅動多 Agent,那我們賣的旗艦賣點就建立在:(a) 隨時可能被官方封鎖的技術上,(b) 可能違反用戶自己帳號 ToS、讓用戶承擔被封號風險的法律灰色地帶上。這比「不實比較 Teamily」的風險大得多,因為它是產品能不能運作的地基。
**Fix**:上市計畫定稿前,必須先確認「用自己的訂閱」具體技術實作方式——如果走的是官方允許的管道(例如 Claude/ChatGPT 有提供訂閱綁定的 API 額度、或用戶自己手動貼 session token 且條款允許),風險大幅降低;如果不是,這句主打訊息要嘛下架,要嘛改包裝成「風險自負」並在文件內免責。@researcher 麻煩查證 Anthropic/OpenAI 消費版訂閱條款是否允許此類第三方自動化調用,這個答案會直接決定整個定位能不能成立。

**2. 對標 Teamily 的護城河太淺,而且法律用語要收斂**
就算 Teamily 目前真的不支援 Ollama/BYO 訂閱,這是功能差距不是架構優勢——他們隨時可以加。如果 90 天上市訊息全押在「Teamily 沒有 X」,一旦對方補上這個功能,我們的核心敘事當場失效。另外研究員自己也標註 Teamily 數字未驗證,若對外文件出現具體比較數字(定價、弱點清單)卻是訓練資料推測,一旦被抓包會傷害整個團隊的可信度,也可能構成不實比較廣告的法律風險。
**Fix**:對外訊息把「打 Teamily」降級為背景脈絡,主打訊息改成正向陳述我們自己的架構優勢(開源、可自架、多供應商),不用點名式比較未經查證的競品數字;任何比較都加「據公開資訊」但先確保真的公開查證過。

**3. 開源失敗模式最可能命中的是「安裝門檻」和「殺手級範例缺席」的組合拳**
支援 10+ 家 API + Ollama 聽起來是賣點,實際上是「配置矩陣爆炸」——新用戶第一次上手要決定用哪個 provider、填哪些 key、Ollama 要不要本機跑模型,這種選擇負擔本身就會勸退 Segment A(最該冷啟動的族群)。如果沒有一個「5 分鐘內看到多 Agent 真的協作出東西」的預設範例(例如內建一組不用任何 API key、純 Ollama 就能跑通的 demo),GitHub star 衝一波後留存會很差。
**Fix**:90 天計畫應把「零門檻 demo」(不用填任何 key、docker-compose up 就能看到 2-3 個 agent 對話產出結果)列為第一週交付物,比任何行銷文案優先。

**4. 商業化路徑目前完全空白,90 天內容易被忽略但會致命**
研究把 Segment B(Agency)定為「第一批付費客戶」,但目前沒有任何東西是「可以賣的」——沒有多租戶、白牌、用量歸戶計費這些 B 最需要的功能,這些都是要寫程式的硬需求,不是行銷訊息能補的。如果 90 天計畫只寫「觸及 B」而沒有對應的產品里程碑,B 這個現金流假設會落空,團隊會發現衝了聲量但沒有營收路徑。
**Fix**:@lead 統整 90 天計畫時,務必把「B 所需的最小付費功能(哪怕只是企業版 waitlist + 手動客製合約)」列為明確的產品里程碑,而不只是行銷/推廣動作。

**5. 安全面完全沒被提到,但這個產品的攻擊面特別大**
多 Agent + 用戶自己的 API key/訂閱憑證 + 可能串接工具(檔案系統、瀏覽器、程式執行)= prompt injection 導致 key 外洩或執行任意操作的風險,遠高於單一 chatbot。開源自架雖然規避了「資料給第三方 SaaS」的疑慮(這是我們對 Segment C 的賣點),但如果我們自己因為安全設計不足出事(例如 agent 被誘導把用戶的 Claude/OpenAI key 送到外部),等於直接打臉自己對企業段的訴求。
**Fix**:90 天內至少要有一份基本的安全模型文件(key 儲存方式、agent 權限隔離、審計紀錄),尤其是在對 Segment C 喊「自架比較安全」之前。
