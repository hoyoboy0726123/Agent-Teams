# Agent Teams
## 開源多 Agent 協作工作空間 — 上市策略

**內部工作稿 v0.1｜2026-09-22｜僅團隊內部流通，不對外**

Note: 開場先講清楚這份簡報的狀態：這是內部工作稿，不是對外發布版。兩個阻斷性問題（訂閱ToS合法性、Segment B最小付費方案）deadline 是本週五(9/25)，結果會直接影響第5頁核心訊息與第7頁成本模型能不能對外講。今天的目的是讓團隊對齊，不是拿去發布。

---

# 問題與機會

- 技術團隊/開發者想要「人類＋多 AI Agent」協作空間，但市面選項要嘛閉源綁定（如 Teamily AI），要嘛開源專案缺乏完整的團隊協作體驗
- 閉源 SaaS 的兩大痛點：**資料不出門做不到**、**被單一供應商綁死**（無法自由切換 Claude/ChatGPT/開源模型）
- 機會：做一個**開源、可自架**的替代方案，原生支援 Claude/ChatGPT 訂閱、10+ 家 API、Ollama 本機模型
- 一句話目標：讓 Agent Teams 開源版成為「自架多 Agent 協作工作空間」的**預設選擇**

Note: 這頁定調「為什麼現在做這件事」。不要點名比較 Teamily 的具體弱點（未查證），把敘事重心放在「我們解決什麼問題」而非「我們比誰好」。

# 目標用戶：三個 Segment

| Segment | 描述 | 核心痛點 | 優先度 |
|---|---|---|---|
| **A｜獨立開發者/新創** | 輕量使用，預算敏感 | 想要低成本試多 Agent 協作，不想被 API 計量嚇跑 | 🥇 60% 資源 |
| **B｜Agency** | 用 Agent 交付客戶專案 | 需要控制權、多供應商彈性，成本次要 | 🥈 25% 資源 |
| **C｜企業 IT/RPA** | 內部導入自動化 | 資料不能出門，安全與稽核要求高 | 🥉 15% 資源 |

- 三個 segment 痛點不同 → 訊息也必須分開講，不能用同一套賣點打全部

Note: 資源分配 60/25/15 是 Week 7-10 冷啟動的規劃假設，來自 dashboard。強調 B 的訊息已經改口（不再談成本），C 目前完全靠「開源自架資料不出門」這條訊息，還沒有安全模型文件支撐，這是待補的產品缺口。

# 競品定位

- **Teamily AI（閉源對標）**：定價、確切弱點目前**未經第一手查證**（researcher 三次嘗試查證被 proxy allowlist 擋下），對外文件不引用具體數字比較
- **相鄰開源專案**（CrewAI、AutoGen/AG2、Dify、n8n agent 功能）多聚焦單一 Agent 編排或工作流自動化，較少做到「人類＋多 Agent 團隊協作空間」這個定位
- 我們的架構差異：原生把 Claude/ChatGPT 訂閱、10+ API、Ollama 放在同一個自架空間裡任意切換
- **決策**：不打「對標 Teamily」的敘事，改成正向陳述自身架構優勢，避免依賴未查證數字的比較風險

Note: 這頁要講清楚為什麼不點名打 Teamily——不是因為打不贏，是因為競品護城河太淺（功能差距不是架構優勢，對方隨時能補），而且我們沒有查證過的數字，講出去有法律和信任風險。

# 關鍵風險與對策

| 風險 | 嚴重度 | 對策 |
|---|---|---|
| 訂閱借用可能違反 ToS / 消費版驗證機制非官方支援 | 🔴 致命 | 本週五(9/25)前小規模實測撞牆點，未解則賣點下架 |
| 對標 Teamily 護城河淺、數字未查證 | 🟠 高 | 降級為正向陳述，不點名比較 |
| 開源安裝門檻高、缺殺手級範例 | 🟠 高 | Week 1-2 交付零 key、純 Ollama 的 docker-compose demo |
| B segment 商業化路徑空白 | 🟡 中 | 最小方案：企業版 waitlist + 手動客製合約 |
| 多 Agent + API key + 工具串接的安全攻擊面 | 🟡 中 | Week 1-2 產出安全模型文件初稿 |

Note: 這是 critic 兩輪紅隊審查的濃縮。第一項是地基風險，其他四項是必須在90天內看到具體交付物、不能只停在文案層次的執行風險。

# 成本模型（規劃假設，待 dogfooding 校正）

**輕量用戶(Segment A)**：訂閱 $20 vs API 計量估算 $29.70 → 訂閱省 ~33%
**重度用戶(Segment B)**：訂閱 $150(市價中位數) vs API 計量估算 $95.04 → **訂閱反而更貴，且大機率撞 rate limit**

- Blended 價格採 70/30 input/output 假設比例，非實測 token 分佈
- 這組數據直接支撐了「訂閱制省錢僅對 Segment A 成立」的訊息決策
- Week 3-6 將用真實 dogfooding log 重跑，才能寫進對外文件

Note: 這頁数字全部來自 analyst 的 dashboard 初稿，务必强调「非實測、規劃假設」，避免有人截圖直接拿去對外用。這也是為什麼 Segment B 訊息必須現在就改，不用等 ToS 答案——量體本身就是第二條獨立的失敗路徑。

# 成功指標（90 天 KPI）

| KPI | 目標 | 說明 |
|---|---|---|
| GitHub Stars | 1,000 | 規劃假設 |
| 活躍自架實例數 | 150 | 規劃假設 |
| Discord/社群成員 | 500 | 規劃假設 |
| 貢獻者數(PR merged≥1) | 25 | 規劃假設 |

- 資源分配依優先度：Segment A 60% / B 25% / C 15%
- 追蹤重點不只是曝光數，而是「首次成功跑通 demo 的比例」——這比 star 數更能反映零門檻策略是否奏效

Note: 這些數字全部標註規劃假設，來自 analyst 的 dashboard，月度成長曲線見 dashboard 原件。KPI 設計呼應 critic 的提醒：開源專案常見失敗模式是衝了聲量沒有留存，所以「首次成功跑通比例」比 star 數更重要，實際追蹤時建議優先看這個指標。
